# dbt + Snowflake Metadata-Driven Data Quality Automation Framework

## Overview

The **dbt Data Quality Automation Framework** is a metadata-driven framework built using **dbt Jinja macros, Snowflake SQL, and Snowflake metadata** to automate source-to-target data quality validation.

The framework is designed to eliminate repetitive manual SQL validation by centralizing table configuration, dynamically generating validation SQL, executing multiple DQ checks, and storing results in a centralized audit table.

Instead of creating separate test scripts for every source and target table, the framework uses configuration metadata to determine:

- Which tables need to be validated
- Which columns form the primary/business key
- Which DQ checks should run
- Which source/target filters should be applied
- Which columns should be excluded
- Which business rules should be executed

The framework can be executed using only:

```text
MODEL_FILTER
PIPELINE_NAME
```

# Framework Components

## 1. `get_count` Macro

The `get_count()` macro executes a SQL query and returns the first value from the first result column.

```jinja
{% macro get_count(q) %}
    {% set r=run_query(q) %}
    {% if execute %}
        {{ return(r.columns[0].values()[0]) }}
    {% endif %}
{% endmacro %}
```

It is used by:

- Count Check
- Duplicate Check
- Null Check
- Data Comparison
- Business Rule Check

---

# 2. Environment Variable Validation

The framework contains a `validate_dq_env_var()` macro that validates required dbt environment variables.

The current dbt implementation supports:

```text
DBT_DPPL_DATABASE_NAME
DBT_SSCTA_DATABASE_NAME
DBT_SSCTA_SSC_GDP_SHARE_DATABASE_NAME
```

The macro checks that:

1. The environment variable exists.
2. It is not empty.
3. It is not still set to the placeholder token.

This prevents the framework from executing against an unresolved database placeholder.

---

# 3. Dynamic Database Resolution

The `resolve_dq_relation_name()` macro dynamically replaces configured database placeholders with their environment-specific database names.

This allows configuration to remain environment-independent.

Conceptually:

```text
Configured Relation
       |
       v
MY_DATABASE.SCHEMA.TABLE
       |
       v
Environment Resolution
       |
       v
Actual Snowflake Database.SCHEMA.TABLE
```

The macro also logs the relation before and after resolution for debugging and traceability.

---

# 4. `DQ_TABLE_CONFIG`

`DQ_TABLE_CONFIG` is the primary metadata/configuration table.

It controls how each source-to-target validation should be executed.

Important metadata includes:

```text
MODEL_FILTER
SOURCE_TABLE
TARGET_TABLE
KEY_COLUMNS
DESCRIPTION
COUNT_CHECK
DUPLICATE_CHECK
NULL_CHECK
STRUCTURE_CHECK
DATA_COMPARISON
SOURCE_FILTER
TARGET_FILTER
EXCLUDED_COLUMNS_SRC
EXCLUDED_COLUMNS_TGT
```

Example:

```text
MODEL_FILTER       = ACCOUNTS
SOURCE_TABLE       = MY_DATABASE.PUBLIC.ACCOUNTS_SOURCE
TARGET_TABLE       = MY_DATABASE.PUBLIC.ACCOUNTS
KEY_COLUMNS        = ["ACCOUNT_ID"]

COUNT_CHECK        = Y
DUPLICATE_CHECK    = Y
NULL_CHECK         = Y
STRUCTURE_CHECK    = Y
DATA_COMPARISON    = Y

SOURCE_FILTER      = 1=1
TARGET_FILTER      = 1=1

EXCLUDED_COLUMNS_SRC = []
EXCLUDED_COLUMNS_TGT = []
```

---

# 5. `DQ_BUSINESS_RULES`

Business-specific validation rules are stored separately from the core DQ framework.

The dbt framework retrieves active rules using:

```sql
WHERE MODEL_FILTER = '<model_filter>'
AND IS_ACTIVE = 'Y'
```

Each rule contains:

- Source table
- Target table
- Rule name
- Rule SQL
- Active flag
- Description

The rule SQL is expected to return a count.

```text
0 failed records
       ↓
     PASS

>0 failed records
       ↓
     FAIL
```

Example business rule:

```sql
SELECT COUNT(*)
FROM MY_DATABASE.PUBLIC.ACCOUNTS
WHERE ACCOUNT_ID IS NULL
```

# DQ Validation Checks

## 1. Count Check

The Count Check compares source and target record counts after applying the configured filters.

Conceptually:

```text
SOURCE COUNT
     |
     v
TARGET COUNT
     |
     +---- Equal ------> PASS
     |
     +---- Different --> FAIL
```

Source query:

```sql
SELECT COUNT(*)
FROM SOURCE_TABLE
WHERE SOURCE_FILTER
```

Target query:

```sql
SELECT COUNT(*)
FROM TARGET_TABLE
WHERE TARGET_FILTER
```

This validates basic source-to-target volume consistency.

---

# 2. Duplicate Check

The Duplicate Check validates duplicate records based on configured key columns.

It supports:

### Single key

```text
ACCOUNT_ID
```

### Composite key

```text
ACCOUNT_ID + SOURCE_SYSTEM
```

The framework dynamically generates:

```sql
GROUP BY <key columns>
HAVING COUNT(*) > 1
```

The check passes only when:

```text
Source duplicate groups = 0
AND
Target duplicate groups = 0
```

---

# 3. Null Check

The Null Check validates NULL values in the configured key columns.

For:

```text
KEY_COLUMNS = ["ACCOUNT_ID"]
```

the framework generates:

```sql
ACCOUNT_ID IS NULL
```

For multiple keys, it dynamically creates:

```sql
KEY1 IS NULL
OR KEY2 IS NULL
OR KEY3 IS NULL
```

The check passes only when both source and target have zero matching NULL records.

---

# 4. Structure Check

The Structure Check compares source and target table metadata using:

```text
<database>.INFORMATION_SCHEMA.COLUMNS
```

It compares:

- Column name
- Data type
- Column count

Configured excluded columns are ignored.

The framework normalizes data types by removing type-size details such as:

```text
VARCHAR(100)
VARCHAR(500)
```

to the base type:

```text
VARCHAR
```

This allows the validation to focus on the configured structural definition.

### Structure validation detects issues such as:

```text
Column added
Column removed
Column renamed
Data type changed
Unexpected schema change
```

---

# 5. Data Comparison

The Data Comparison check performs a bidirectional source-to-target comparison.

The framework dynamically determines common source and target columns after applying configured exclusions.

The comparison follows:

```text
SOURCE
  MINUS
TARGET

UNION

TARGET
  MINUS
SOURCE
```

Conceptually:

```text
           SOURCE
              |
              v
        SOURCE MINUS TARGET
              |
              +----------------+
                               |
                               v
                              UNION
                               ^
                               |
              +----------------+
              |
        TARGET MINUS SOURCE
              |
              v
            RESULT
```

The final difference count determines the result:

```text
DIFF = 0
   ↓
PASS

DIFF > 0
   ↓
FAIL
```

This provides bidirectional reconciliation rather than validating only one direction.

---

# 6. Business Rule Check

After table-level checks are completed, the framework executes active business rules associated with the selected `MODEL_FILTER`.

Example:

```text
MODEL_FILTER = ACCOUNTS
```

The framework retrieves all active rules:

```text
ACCOUNT_ID_NOT_NULL
ACCOUNT_STATUS_VALID
ACCOUNT_BALANCE_VALID
...
```

and executes each rule dynamically.

The framework records the result as:

```text
BUSINESS_RULE_<RULE_NAME>
```

Example:

```text
BUSINESS_RULE_ACCOUNT_ID_NOT_NULL
```

# Metadata-Driven Design

The main architectural advantage is that validation logic is separated from table-specific configuration.

Traditional approach:

```text
Accounts SQL
Customer SQL
Orders SQL
Transactions SQL
Products SQL
...
```

Metadata-driven approach:

```text
                 DQ_TABLE_CONFIG
                        |
        +---------------+---------------+
        |               |               |
     ACCOUNTS        CUSTOMER         ORDERS
        |               |               |
        +---------------+---------------+
                        |
                        v
                 SAME DQ ENGINE
```

This allows new tables to be onboarded primarily by adding configuration metadata rather than creating a new framework implementation.

---

# Configuration-Driven Execution

Each check can be independently enabled or disabled.

Example:

```text
COUNT_CHECK       = Y
DUPLICATE_CHECK   = Y
NULL_CHECK        = Y
STRUCTURE_CHECK   = Y
DATA_COMPARISON   = Y
```

A table can therefore run only the validations relevant to its requirements.

For example:

```text
COUNT_CHECK       = Y
DUPLICATE_CHECK   = Y
NULL_CHECK        = N
STRUCTURE_CHECK   = Y
DATA_COMPARISON   = Y
```

The core framework code does not need to be changed.

---

# Source and Target Filters

The framework supports table-specific filters.

Example:

```text
SOURCE_FILTER = CURRENT_FLAG = 'Y'

TARGET_FILTER = CURRENT_FLAG = 'Y'
```

This allows validation to focus on the required business/data scope instead of always comparing entire tables.

The default is:

```sql
1=1
```

---

# Column Exclusions

The framework supports configurable source and target exclusions.

Example:

```text
EXCLUDED_COLUMNS_SRC = ["LOAD_TIMESTAMP"]
EXCLUDED_COLUMNS_TGT = ["LOAD_TIMESTAMP"]
```

This is useful for technical columns that are expected to differ between source and target.

It also allows the framework to focus data comparison and structure validation on business-relevant columns.

# Auditability and Traceability

Each framework execution generates a unique:

```text
RUN_ID
```

The run ID is propagated to every DQ result.

This provides traceability:

```text
RUN_ID
  |
  +--> Pipeline
  |
  +--> Model
  |
  +--> Source Table
  |
  +--> Target Table
  |
  +--> DQ Check
  |
  +--> PASS / FAIL
  |
  +--> Details
  |
  +--> Executed SQL
```

This is particularly useful for regression testing and production support.

# Why Metadata-Driven DQ?

Without metadata-driven automation:

```text
Table 1
  ↓
Write SQL
  ↓
Execute
  ↓
Validate
  ↓
Document

Table 2
  ↓
Write SQL
  ↓
Execute
  ↓
Validate
  ↓
Document

Table 3
  ↓
...
```

With the framework:

```text
                CONFIGURATION
                      |
                      v
              +---------------+
              | DQ FRAMEWORK  |
              +-------+-------+
                      |
        +-------------+-------------+
        |             |             |
       DQ            DQ            DQ
     CHECKS        CHECKS        CHECKS
        |             |             |
        +-------------+-------------+
                      |
                      v
                 DQ_RESULTS
```

The validation engine becomes reusable infrastructure instead of a collection of one-off SQL scripts.

# Resume-Ready Project Description

**Designed and developed a metadata-driven Data Quality Automation Framework using dbt, Snowflake SQL and Jinja macros to automate source-to-target validation across multiple data pipelines and datasets.**

### Key Contributions

- Designed and implemented a reusable **dbt-based Data Quality Automation Framework** using Jinja macros and Snowflake SQL.
- Developed automated **Count, Duplicate, Null, Structure, Data Comparison and Business Rule** validations.

- Centralized validation results with **RUN_ID, pipeline name, model, check type, status, details and executed SQL** for auditability.
- Designed the framework for scalable onboarding of multiple datasets without duplicating validation code.
- Automated a benchmark scenario of approximately **175 tables**, reducing validation execution effort from **15–20 hours manually to ~20 minutes**, representing approximately **98% execution-time reduction**.
